# XFS kernel shim

The XFS backend compiles the Linux kernel's `fs/xfs` sources unmodified
(`third_party/linux-xfs/`, plus the kernel's `lib/rbtree.c` in
`third_party/linux-lib/`). They expect the Linux kernel API, so
`backends/xfs/shim/` supplies a small implementation of it on top of the host
block layer and the C runtime. The shim also shadows a few kernel headers
(`xfs_super.h`, `xfs_buf.h`, `xfs_sysfs.h`, `xfs_qm.h`, ...) with versions that
carry only what the backend needs.

Changes to the kernel files are made only as patches in
`third_party/linux-xfs-patches/`; the vendored tree is checked byte for byte by
`tools/vendor-xfs.sh --verify`. A shim is preferred over a patch, because each
patch has to be carried over at every kernel update.

## What the shim provides

| Area | Implementation |
|---|---|
| Trace points | No-op inline stubs, generated by `tools/gen-trace-stubs.sh`. |
| Sleep and wake | Wait queues, completions, semaphores (lock-free fast path), `wait_var_event`, `wake_up_bit` on pthread / SRW condition variables (`wfs_sync.h`, `wfs_sched.c`). `schedule()` is used only inside the shim's wait helpers. |
| Work queues and threads | `alloc_workqueue`, delayed work, `kthread_run/stop` (for `xfsaild`) run on real threads (`wfs_sched.c`). |
| Locks | `rw_semaphore` is a reader-preferring lock built from an SRWLOCK and a CONDITION_VARIABLE. A bare SRWLOCK is writer-fair and deadlocks on the kernel's nested read locks. |
| Log and block I/O | A `struct bio` that collects an iclog's segments and issues `blk_write` and `blk_flush` (`REQ_PREFLUSH`/`FUA`) through the host API (`bio.c`). Completions run inline. |
| Buffer cache | `buf.c` implements the kernel buffer contract: locks, pins, delayed-write lists, write-back, shutdown on a write error, single-flight reads and LRU. |
| Lists and trees | Lists, hlist and ERR_PTR in `wfs_kcompat`/`wfs_types`; the extent-busy rbtree is the kernel's own `lib/rbtree.c` (LLP64 patch `0001-rbtree-uintptr`). |
| Per-CPU data | A one-CPU model: per-cpu data is a single instance under the CIL lock. Correct, with no scalability. |
| VFS and page cache | No page cache: `i_mapping`, `filemap_*`, `truncate_pagecache_range` and similar are no-ops or answer "clean". Data I/O is the backend's own direct write path. |
| Allocation | `wfs_alloc` counts live bytes against a cap; see "Allocation failure" in `xfs-backend.md`. |
| Atomics, static keys, sysfs, freezer, memalloc flags | Trivial definitions. |

Not supported (rejected at mount time, so the code paths never run): realtime
intents and writes, quota accounting (dquot items are stubs), and the
`exchmaps` file-exchange machinery.

## LLP64

On Windows x64 (mingw) `long` is 32 bits; the kernel assumes 64. The shim
forces `int64_t`, `uint64_t`, `intmax_t` and `loff_t` to `long long` on every
target, so `u64`, `xfs_off_t` and the `%llx` formats are identical on host and
Windows builds, and the native test build exercises the same type identities.
`unsigned long` appears in the vendored code only as a bitmap word, and all bit
numbers used are below 32. `backends/xfs/shim/LLP64.md` lists the hazards and
the audit of the vendored code.

## Finding what the shim still has to provide

`tools/xfs-shim-probe.sh --pre` compiles each vendored kernel file with
`-fsyntax-only` against the shim and `tools/xfs_shim_needs.py` summarises the
result: missing kernel APIs, undeclared XFS functions, struct members missing
from shim structs and incomplete types. Run it after a kernel update. Counts
are first-order; fixing headers can expose further errors.
